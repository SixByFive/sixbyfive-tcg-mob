## Context

The `deleteBinder` mutation existed in the backend (`DELETE /binder/:id`, soft-delete by default) and `useBinderActions.js` already exposed a `deleteBinder` action. There was no UI entry point in the mobile app to trigger it from the binder editor.

## Decision

- Added optional `onDelete` prop to `components/binders/BinderOptionsModal.js`. When provided, renders a destructive "Delete binder" button below the Cancel/Save row.
- In `app/binder/[id]/edit.js`, wired `deleteBinderServer` from `useBinderActions`, implemented `handleDelete` that shows a native `Alert.alert` confirmation (destructive style, shows binder name), then calls `deleteBinder` and navigates back on success.
- Passed `onDelete={handleDelete}` to `BinderOptionsModal`.

The backend soft-deletes by default (`isDeleted = true`). Permanent deletion requires passing `permanent: true` to the mutation — not exposed in the UI.

## Consequences

- Delete is accessible via the settings (gear) icon on the binder editor screen.
- Confirmation alert prevents accidental deletion.
- `BinderOptionsModal` remains usable without `onDelete` — the button simply doesn't render.
- Soft delete means data is recoverable server-side even if the user deletes by mistake.
